# DSA: capability-first data structures and algorithms

**An experiment in writing each algorithm against the weakest capability it actually needs,
rather than against a concrete data structure. The design is then stress-tested by composing
the library into solutions for more than a thousand LeetCode problems.**

C# · .NET 10 · ~10,300-line core library · 26 data-structure families · 17 algorithm families ·
1,105 problem solutions · 7,171 test methods · 2,169 benchmarks
<sub>(measured September 2026)</sub>

---

## The idea

Textbook code welds algorithms to data structures: Dijkstra takes a `Graph`, and binary search
takes an `int[]`. This library separates every structure along three independent axes, which
are written up in [ARCHITECTURE.md](ARCHITECTURE.md):

| Axis | Question it answers | Example |
|---|---|---|
| **Representation** | Where the data lives, and what reaching it *costs* | array, linked, arena and indices, or computed from geometry |
| **Topology** | Which shapes are admissible | general graph, DAG, tree, heap order, BST order |
| **Operations** | The algorithm built on the other two | fold, shortest path, sort, search |

A binary heap shows why the axes are separate. It has *tree* topology but *array*
representation, so it is one logical shape with a completely different physical layout and cost
profile.

### What the separation buys

- **Stronger promises let algorithms do less work.** Graph topologies form a refinement chain:
  `IGraphTopology → IDagTopology → ITreeTopology`. Each tier adds no members, only a stronger
  guarantee. The same fold therefore comes in three tiers. `CheckedFold` accepts any graph and
  defends against cycles at run time, `DagFold` knows there are no cycles and skips that
  defence, and `TreeFold` also skips visited-tracking. Each pays only for the defence its tier
  doesn't already rule out.
- **Abstraction without runtime cost.** Topology choices are `struct` witnesses implementing
  `static abstract` interfaces, for example `Heap<T, TOrder> where TOrder : struct,
  IHeapOrder<T>`. The JIT specializes each instantiation into direct, non-virtual calls with no
  boxing.
- **One algorithm, one injected axis.** Dijkstra is A* closed over a zero heuristic, not a
  second implementation.
- **Complexity is a contract.** The type system can't state that `Heap` is O(log n) only
  because its backing array's `Get` is O(1). The obligation is written on the contract and the
  consequence on the algorithm, so a well-meant representation swap can't silently regress
  performance.

ARCHITECTURE.md also gives a checklist for adding anything. Name the operations and the laws
first, classify each law (topology witness, open runtime object, precondition, or complexity
law), and add an interface only when a second implementation exists to justify it. Worked
examples cover heaps, binary search, union-find, merge sort, DFS, topological sort and
all-pairs shortest paths.

## What's in it

- **Data structures:** dynamic array, deque, stack and queue (composed, not duplicated), hash map
  and set, heap, disjoint set, Fenwick and segment trees (including lazy propagation), tries,
  suffix array, suffix automaton and suffix tree, Aho-Corasick, LRU and LFU caches, interval
  sets, rolling hashes, and graph, grid and tree families.
- **Algorithms:** shortest paths (Dijkstra/A*, Bellman-Ford, Floyd-Warshall), connectivity
  (components, strongly connected components, bridges and articulation points), minimum spanning
  trees, topological sort, bipartiteness, string matching (KMP, Z-function, Manacher),
  folding, reducing and walking engines, dynamic programming, backtracking, searching and
  sorting.

## The stress test: 1,105 problems

A library design proves itself only when many consumers use it. An agent workflow (Claude Code,
scripted under [`.claude/workflows/`](.claude/workflows/)) worked through a manifest of LeetCode
problems. Each solution was built by composing this library's primitives and had to pass a real
build and test run before it was recorded. Problems that needed a primitive the library lacked
were logged as blocked, with the reason, for a follow-up pass.

- **1,105 solutions**, most of which compose the library's own structures and algorithms rather
  than the BCL's.
- Each solution keeps every strategy it tried, the naive baseline included. BenchmarkDotNet
  compares them with memory diagnostics over seeded, reproducible workloads, and a test suite
  checks that every strategy agrees with every other.
- **The architecture rules are tests.** Layering tests keep the tiers in order (core library,
  domain, problems, harnesses), and coverage tests check that every problem's strategies are
  exercised.

The core library's design is mine, and much of it was implemented with AI agents. The problem
corpus was generated by an agent workflow. The code is checked by my code-conformance linter,
the Go prototype that became [Nomos](https://github.com/kevinmettias/nomos).

## Try it

Requires the .NET 10 SDK.

```sh
# the core library's tests (the full suite is in three test projects)
dotnet test DSAExperimentation.Tests/DSAExperimentation.Tests.csproj

# benchmark every strategy for one problem
dotnet run -c Release --project DSAExperimentation.Benchmarks -- --filter "*AccountsMerge*"
```

## Layout

| Project | Contents |
|---|---|
| `DSAExperimentation` | The library: `DataStructures/`, `Algorithms/` and `Domain/` |
| `DSAExperimentation.LeetCode` | One folder per problem, plus the registration harness |
| `DSAExperimentation.Tests` | Library, architecture and per-problem tests |
| `DSAExperimentation.LeetCode.Tests` | Tests of the seams between problems and the library |
| `DSAExperimentation.Benchmarks` | BenchmarkDotNet suites, one per problem, plus strategy-swap comparisons |
| `DSAExperimentation.Benchmarks.Tests` | Checks that benchmark arms agree and that their workloads are reproducible |
